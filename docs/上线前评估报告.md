## 1. 项目现状梳理

### 1.1 技术栈

| 层 | 技术 | 证据 |
|---|---|---|
| 客户端 | 微信小程序原生（无框架、无 TS、无构建工具） | `app.json`、`pages/*`、根目录**无** `package.json` |
| 云端 | 微信云开发云函数 `docsProxy`（单函数 relay） | `cloudfunctions/docsProxy/index.js` |
| 运行时 | Node.js（容器 TZ=UTC，代码内固定 +8h 对齐北京时） | `tencentdocs.js:779-785` |
| 数据底座 | **腾讯文档智能表格 smartbook API**（8 张表），非传统数据库 | `tencentdocs.js:39-48` 的 `TABLE` 常量 |
| 依赖 | `wx-server-sdk ~2.6.3`（唯一运行时依赖） | `cloudfunctions/docsProxy/package.json:6-8` |
| 本地回退 | `utils/mock.js`（前端）+ `index.js` 的 `mockHandler`（云端演示） | 三套实现需手工保持一致 |
| 测试 | 纯 Node 脚本（11 个套件），**无单测框架、无覆盖率工具** | `tools/regress-all.js` |
| E2E | `miniprogram-automator`，README 自述**路线已放弃** | `test/README.md:3-9` |

### 1.3 外部服务与数据

- **腾讯文档开放平台**：应用级 `access_token` + `client_id` + `file_id`，读写 8 张表；配额 **150 次/分钟/fileID**。
- **微信云开发**：云函数承载 + 云数据库**未使用**。
- **微信开放能力**：仅 `wx.scanCode`（扫码），**未使用** `getUserProfile` / `getLocation` / `getPhoneNumber` 等隐私敏感 API。
- **8 张表**：`users`（工号/姓名/角色/班级/openid）、`materials`、`tools`、`requisitions`、`borrow`、`stock_io`、`access`（门禁）、`logs`。

| 环节 | 现状 | 证据 |

## 2. 上线就绪度评估

### 2.1 代码质量

| 项 | 结论 | 说明 |
|---|---|---|
| 自动化测试 | ⚠️ 有覆盖但形态原始 | 11 套件 / 159 项断言，**0 前端单测、0 覆盖率**、E2E 已弃用 |
| 静态检查 | ❌ 缺失 | 无 eslint / prettier / tsconfig，根目录无 `package.json` |
| 错误处理（写） | ✅ 通过 | 14 处写调用全部 `callFull + noFallback:true`，传输失败必返 503，不会假成功 |
| 错误处理（读） | ❌ 静默误导 | `utils/api.js:49-56` 读失败**回退本地 mock 并当正常数据渲染**；9 页中 7 页把"云端挂了"显示成"没有数据" |
| 单元可测性 | ⚠️ | `tencentdocs.js` 2191 行单文件；`utils/mock.js` 640 行复制粘贴了生产逻辑，改一处要改三处 |
| 死代码 | ⚠️ | `utils/identity.js:50-57` 的 `login()` 无姓名校验且**前端从未调用**（潜在误用风险） |

### 2.2 安全性

| 项 | 结论 | 说明 |
|---|---|---|
| 服务端 RBAC | ✅ 通过 | `index.js:556-580` 由 openid→users 表推导真实身份，`data.user/actor` 一律服务端覆盖 |
| IDOR 防护 | ✅ 通过 | `listMine`/`cancelReq`/`returnTool` 均做对象级归属校验 |
| **认证强度** | ❌ 阻塞 | 登录仅凭「工号+姓名」，而姓名可由 `findUser` 匿名枚举 → 可冒用任意教师/管理员 |
| **默认账号** | ❌ 阻塞 | `A001/管理员` 等 4 行默认账号仍启用且 openid 为空，凭证公开在仓库文档中 |
| 密钥管理 | ⚠️ 风险 | 真实 `access_token` 明文在 `cloudfunctions/docsProxy/env.local.js`，**随云函数部署包上传到云端**（已 gitignore，未进 git 历史） |
| 数据坐标 | ⚠️ 风险 | `fileID` + 8 个 `sheet_id` 硬编码在源码（`tencentdocs.js:39-48`） |
| 输入校验 | ⚠️ 风险 | 数量/库存/角色校验扎实；`src`/`note` 无白名单 → 可伪造「冲销」标记使统计被静默抹除 |
| CSV 注入 | ⚠️ 风险 | `csvCell` 只转义引号/逗号/换行，不防 `=`/`+`/`-`/`@` 开头的公式注入 |
| 依赖漏洞 | ⚠️ 风险 | `wx-server-sdk ~2.6.3`（2022-01 发布，最新 4.0.2）+ **无 lockfile** → 构建不可复现；具体 CVE 未验证（镜像源不支持 audit） |
| 注入面 | ✅ 通过 | 用户输入从不参与 URL/表名/列名拼接（列名来自固定 `COL` 映射） |

> **本轮已修复**：`findUser` 的 openid 绑定副作用（抢绑他人账号）、`exportData` 越权导出管理员专属日志/门禁、`diag` 匿名可打生产 API、盘点页生产 404。

### 2.3 性能

| 项 | 结论 | 说明 |
|---|---|---|
| 读放大 | ⚠️ 风险 | `getRecords` 分页拉**全表**后内存过滤；`logs`/`access` 增长后每次读都全表扫描，1000 行即 10+ 次 API 调用，配额 150 次/分将被打满 |
| 缓存 | ✅ 通过 | 10s TTL + 写后失效 + `_writeSeq` 序号机制，避免把横跨写入的分页结果回填缓存 |
| 前端 setData | ⚠️ 风险 | `usage.js:56` 把完整 `rank` 数组传两遍；`inventory.js:46-51` 全量数组存两份副本 |
| 长列表 | ✅ 通过 | 全部列表分页（PAGE 30/50），23 个 `wx:for` 全有 `wx:key` |
| 定时器 | ✅ 通过 | 零 `setInterval`、零轮询 |
| 并发安全 | ❌ 阻塞 | `withWriteLock` 是**实例级内存 Promise 链**，多实例部署下互斥完全失效；`withWriteIdem` 的 Map 同样实例级 |
| 超时 | ⚠️ 风险 | HTTP 单请求 20s + 429 退避重试，最坏耗时可能超云函数 20s 硬超时；无 `config.json` 固定超时（依赖控制台手工设置） |

## 4. 总结与风险提示

### 4.1 明确结论

> ## ⚠️ 有条件上线
>
> **可用于**：体验版 / 小范围内部试用（教师 3–5 人，真实数据仅教师操作）

> **暂不具备**：「提交微信审核并对全校师生开放」的条件

**理由分层：**

**A. 本轮已消除的阻塞（代码已改、已加自动化防线）**

**B. 仍需在「上线前」清零的阻塞（不可绕过）**

4. **无恢复脚本、无回滚预案、无 git 版本锚点** —— 三条回滚路径全缺，线上出事无法有序回退。
5. **隐私合规缺口** —— 实际采集个人信息但无声明入口；现有文档还给出了"零风险"的错误结论。

7. **主体资质错配**（个人主体承载校内业务），平台侧动作周期长。
