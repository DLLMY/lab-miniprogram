# 实训室物品管理系统 · 功能评估与补充方案报告

> 评估日期：2026-10-24
> 评估对象：`lab-miniprogram`（微信小程序 + 云函数 docsProxy + 腾讯文档数据底座）
> 评估方法：① 全量源码走查（9 个页面 / 云函数 23 个 action / 前端回退层）；② 线上真实数据只读核对；③ 对照仓储管理系统（WMS）、办公审批（OA）及微信小程序交互惯例逐项比对
> 数据底座：8 张表（users / materials / tools / requisitions / borrow / stock_io / access / logs）

---

## 0. 结论摘要

**总体判断：功能骨架完整、工程防护质量高于同类小型系统，但存在 1 个 P0 级账务缺陷，以及若干"闭环断点"与"行业标配缺失"。**

| 维度 | 评价 |
|---|---|
| 功能覆盖 | 主流程闭环（建档→入库→申请→审批→出库→借还→统计）已贯通 |
| 工程质量 | 优：写锁 + 幂等 + 写后回读自愈 + 服务端校验，防护强度超出一般小系统 |
| **账务正确性** | **⚠️ 存在 P0 缺陷：审批领用扣库存不写出入库流水，导致流水不完整、库存无法对账** |
| 交互一致性 | 中：扫码"只查不办"、归还权限、确认机制等与常规习惯有偏差 |
| 行业标配 | 缺：盘点、期初建账、导出、批量、分页、库位/批次维度、逾期管理 |

> **最需优先处理**：审批出库不记流水（P0）。它使"出入库流水"这一核心账本不完整，是此前实测发现"库存与流水推算期初为负数"的真实原因之一，且违反"每笔库存变动必有流水"的账务铁律。

## 2. 做得好的地方（优先保留的设计）

评估不应只看缺口，以下防护设计明显优于同类小型系统，后续扩展时应继续沿用：

1. **写操作三重防护**：`withWriteLock`（串行化）+ `withWriteIdem`（5 秒幂等窗口）+ 写后回读校验/自愈。已实测挡住"前端双发导致库存双倍扣减"的真机问题。
2. **服务端参数校验前置**：数量、方向、ID 存在性等均在服务端校验，不信任客户端。
3. **时间统一为北京时间**：容器 TZ=UTC 已用固定 +8 偏移修正，单据时间不再慢 8 小时。
4. **真实/演示严格隔离**：写入口统一 `noFallback`，避免传输失败静默回退 mock 造成"假成功"。
5. **角色三值契约 + 双向映射**：容忍表里"通过/拒绝/校长"等脏值，收敛到 student/teacher/admin。
6. **状态映射表 TR 集中维护**：中英文状态双向映射，便于后续扩展。

## 3. 差异说明（与常规操作习惯 / 行业标准的偏差）

### 3.1 A 类 · 账务与流程（最严重，直接影响数据可信度）

#### A1 【P0】审批领用扣库存，但不写出入库流水
- **行业惯例**：每一笔库存变动必须有对应的库存流水（stock ledger），流水是唯一的对账与审计依据。
- **当前现状**：`approve` 通过耗材申请时执行 `updateRecord(materials, stock: cur - qty)` 并改申请单状态、写 logs，**但没有 `addRecord('stock_io')`**。全系统仅 `io` 手动登记与 `addMaterial` 建档两处写流水。
- **影响**：
  1. 出入库流水**不能反映全部库存变动**——"领用出库"这最主要的出库方式在流水里完全消失；
  2. 库存与流水**必然对不上**（实测"推算期初为负数"的主要原因之一，此前误判为"删流水不调库存"）；
  3. 无法做库存追溯、审计、月度消耗统计。
- **建议**：审批通过耗材时同步写一条 `stock_io`（方向=出库、数量=申请量、物品ID、操作人=申请人、备注=「领用申请 RQ-xxx」）；同时提供历史补录脚本，把已通过但未记流水的领用补成出库流水。

#### A2 【P1】审批出库与手动出库双轨并行、互无关联
- **行业惯例**：出库必须关联单据（申请单/领料单），且同一单据不可重复出库。
- **当前现状**：审批通过自动扣库存；同时 `io` 页可对同一耗材再手动出库一次，两者无单据关联，无"已通过未出库/已出库"状态机。
- **影响**：存在重复出库风险；无法回答"这笔出库对应哪张申请单"。
- **建议**：出库登记时可选关联申请单号；申请单增加"出库状态"；已出库的申请单不允许再手动重复出库。

#### A3 【P1】无库存盘点功能
- **行业惯例**：定期（月/季）盘点，生成盘点单，实盘与账面差异做盈亏调整并留痕。
- **当前现状**：完全没有盘点入口，库存只能靠流水累加，账面与实物长期偏离无法校正。
- **影响**：账实不符无法发现与修正，是实训室资产管理的硬伤。
- **建议**：新增盘点页（按物品列账面数→录实盘数→生成差异→一键调整库存并写盘点流水）。

#### A4 【P1】无期初建账流程
- **行业惯例**：系统启用时录入"期初库存"，作为后续所有变动的基准。
- **当前现状**：`bootstrap-schema` 只建表结构与种子示例，无"期初库存录入/确认"环节；库存基线由零散流水累加而来，已不可精确追溯。
- **建议**：增设期初建账页（录期初数量→写「期初入库」流水）；正式上线前做一次实物盘点重置基线。

#### A5 【P2】出库无用途 / 领用人记录
- **行业惯例**：领料必填用途、成本中心或项目名称，便于核算与追溯。
- **当前现状**：`requisitions` 表有「用途说明」列，但代码恒写 `reason: ''`，学生申请弹窗也无用途输入项。
- **建议**：申请弹窗加"用途"输入（可预置实训项目选项），写入 `reason`，并在审批列表与详情展示。

#### A6 【P2】驳回无原因
- **行业惯例**：驳回需填写原因，申请人可见，便于改正重提。
- **当前现状**：拒绝只改状态为「已拒绝」并记审批人，无原因字段与填写入口。
- **建议**：`requisitions` 增加「驳回原因」列，拒绝时必填，学生侧"我的申请"可查看。

#### A7 【P2】申请提交后不可撤销
- **行业惯例**：OA 中待审批单据允许申请人撤回。
- **当前现状**：无任何撤销/撤回 action，学生提交后只能等审批或找管理员改表。
- **建议**：新增"撤销申请"（仅待审批状态可撤，写 logs）。

#### A8 【P3】无多级 / 会签审批
- **行业惯例**：贵重物品或超量领用需多级审批。
- **当前现状**：单级审批，教师一人即可通过任意数量。
- **建议**（若需）：按数量或物品价值设阈值，超阈值转管理员审批。

### 3.2 B 类 · 交互与使用习惯

#### B1 【P1】扫码"只查不办"——最大交互断点
- **常规习惯**：扫码枪/PDA 扫完即进入对应业务单据（扫码入库、扫码出库、扫码盘点）。
- **当前现状**：教师扫耗材落在详情页，吸底条**没有任何入库/出库按钮**（显示"当前物品在库，无需操作"），必须退回首页→进 io 页→在 picker 里重新选一遍刚扫过的物品。
- **影响**："扫了白扫"，实操效率低于手工选择，与"扫码提效"的初衷相悖。
- **建议**：详情页按角色补「入库登记 / 出库登记」入口，携带 `?id=xxx&dir=in|out` 跳 io 页并自动选中该物品（io 页 `onLoad` 已支持参数，`tab=new` 是现成先例），保持"登记只在 io 页"的单一职责。

#### B2 【P1】工具归还只能教师操作
- **常规习惯**：借用人在自助终端/小程序自助归还，或扫码即还；管理员仅做确认。
- **当前现状**：`returnTool` 只有教师/管理员可触发，学生侧"已借出"工具无任何归还入口。
- **影响**：教师成为归还瓶颈；学生无法自助完成闭环。
- **建议**：增加学生自助"申请归还"（或扫码归还），教师侧确认；或直接开放学生归还并记 logs。

#### B3 【P1】工具借用无期限、无逾期管理
- **常规习惯**：借出登记"应还日期"，逾期自动标记、提醒、统计。
- **当前现状**：`borrow` 表有「计划归还」列，但代码恒写 `plan: ''`；无逾期判定与提醒。
- **建议**：借出时写入计划归还日期（可按工具类目设默认借期）；列表/我的申请里标记"已逾期"；首页给教师逾期提醒。

#### B4 【P2】出入库提交无二次确认
- **常规习惯**：涉及库存/金额变更的操作提交前弹确认，防误触。
- **当前现状**：`io` 提交直接发起（`io.js:203` 的弹窗仅是"物品已存在"的错误提示，非确认）；仅删除用户、申请、重置演示有确认。
- **建议**：出入库提交前弹确认（物品/方向/数量），尤其是出库。

#### B5 【P2】无批量操作
- **常规习惯**：WMS 必备批量入库、批量审批、批量建档。
- **当前现状**：全部单次操作。审批若有 20 张单需点 20 次。
- **建议**：审批页加"全选通过"；io 页支持连续扫码批量入库。

#### B6 【P2】无分页 / 上拉加载
- **常规习惯**：列表分页或无限滚动。
- **当前现状**：`listMaterials/listTools/pending` 全量返回；流水硬编码 `limit: 30`；无 `onReachBottom`。
- **影响**：数据量上千后首屏卡顿、流量浪费。
- **建议**：列表加分页参数 + 上拉加载；流水改为可翻页。

#### B7 【P2】库存一览只读
- **常规习惯**：库存列表支持快捷改库存、调库位、快捷入库。
- **当前现状**：库存页只能点击进详情，不能就地调整。
- **建议**：教师侧在库存项加"快捷入库/出库"入口（复用 B1 的跳转逻辑）。

#### B8 【P2】出入库流水无筛选
- **常规习惯**：流水按时间范围/物品/方向/操作人筛选，是对账的基本能力。
- **当前现状**：只有最近 30 条，无任何筛选。
- **建议**：流水页加筛选条（时间区间、物品、方向、操作人）。

#### B9 【P2】删除用户为物理删除
- **常规习惯**：停用/禁用而非删除，保留历史可追溯。
- **当前现状**：虽有二次确认，但直接删行；提示语称"历史记录保留"，但用户行消失后 `usage`/`listMine` 中该工号将显示为裸 ID。
- **建议**：改为"停用"（状态置为停用并拦截登录），删除仅管理员在清理脏数据时可用。

#### B10 【P2】搜索范围与体验不统一
- **当前现状**：首页模糊搜索支持名称/规格/位置/编码 + 容错；库存页搜索**只匹配名称与 ID**；均不能搜用户/申请单（管理员视角需要）。
- **建议**：库存页搜索复用同一模糊能力；管理员搜索扩展至用户与申请单。

#### B11 【P3】高频功能不在一级入口
- **常规习惯**：高频操作放一级（tabBar）。
- **当前现状**：tabBar 仅「工作台/我的」，库存、审批、出入库均为二级页，教师高频使用需多点一层。
- **建议**：评估将「库存一览」或「审批」提为 tab；或在首页按角色动态调整快捷区。

#### B12 【P3】无物品图片
- **常规习惯**：物品档案配图，便于实物比对。
- **当前现状**：无图片字段。
- **建议**：materials/tools 增加图片列（腾讯云存储或腾讯文档附件）。

#### B13 【P3】只识别码、不生成码
- **常规习惯**：系统为物品生成并打印条码/二维码标签。
- **当前现状**：`snapshot` 提供 `qr` 字段（=物品ID），但无绘制/打印功能，实物码需外部工具生成。
- **建议**：按已交付的《全生命周期设计方案》P2 落地：前端 canvas 绘码 + 支持打印/保存。

#### B14 【P3】无新手引导
- **常规习惯**：首次使用有引导或空状态教学。
- **当前现状**：无。
- **建议**：首次进入按角色给一次操作指引（可关闭）。

### 3.3 C 类 · 数据模型

#### C1 【P2】库存是单一数值，无库位维度
- **行业惯例**：库存 = 物品 × 库位（× 批次），支持一物多位、库位间调拨。
- **当前现状**：`loc`（存放位置）只是文本标签，库存是整表单一数值，不能一物多库位，不能调拨。
- **建议**：若库位管理需求强，引入库存明细维度；短期至少支持"一物多位"文本约定与库位筛选。

#### C2 【P2】无批次 / 有效期管理
- **行业惯例**：耗材（尤其化学试剂、焊锡丝、电池）需批次与效期，近效期预警。
- **当前现状**：无批次与效期字段。
- **建议**：若涉及试剂/危险品，增加批次与有效期列 + 近效期提醒。

#### C3 【P3】无供应商 / 入库来源
- **行业惯例**：入库区分采购、捐赠、调拨、盘盈，并关联供应商。
- **当前现状**：`stock_io` 只有备注，无来源类型与供应商。
- **建议**：增加入库来源枚举（采购/捐赠/调拨/盘盈/期初）；按需建供应商表。

#### C4 【P3】无计量单位换算
- **行业惯例**：支持"箱→个"多单位与换算率。
- **当前现状**：单单位。
- **建议**：按需增加换算率。

#### C5 【P3】状态写法三套并存（技术债）
- **当前现状**：`tools.status` 用「在库/借出」，`borrow.status` 用「借出中/已归还」，前端经 `TR.borrowRev` 映射为「借出/已还」——同一业务概念三种写法，靠映射表维系。
- **建议**：维持 TR 集中映射即可（当前已正确），新增状态时必须同步 TR，避免硬编码字符串散落。

#### C6 【P3】部分字段有列未用
- **当前现状**：`materials.status`、`borrow.plan` 有列但恒空；`access`（门禁）有表有 action 无页面。
- **建议**：要么启用、要么在设计文档中标注为预留，避免误以为已实现。

---

### 3.4 D 类 · 管控与报表

#### D1 【P1】无数据导出
- **行业惯例**：库存清单、流水、盘点表可导出 Excel/CSV，用于对账与上报。
- **当前现状**：无任何导出能力，全部数据只能在小程序内看。
- **建议**：导出 CSV（云函数生成 → 返回文件/复制链接）；至少支持库存清单与出入库流水。

#### D2 【P2】库存预警无主动触达
- **行业惯例**：低于安全库存时推送/红点提醒。
- **当前现状**：仅在库存页显示"预警 N 项"数字与红色水位条，无推送、无首页提醒。
- **建议**：首页给教师/管理员增加预警红点与清单入口；必要时订阅消息推送。

#### D3 【P2】无报表
- **行业惯例**：月度消耗、领用统计、资产清单、借用逾期表。
- **当前现状**：只有"使用概况"（操作量排行），无业务报表。
- **建议**：使用概况页增加"月度领用 Top10""耗材消耗趋势""工具借用周转"。

#### D4 【P2】无全量操作日志查询页
- **行业惯例**：管理员可查全量操作日志（谁在何时做了什么）。
- **当前现状**：`logs` 表全程写入（已有 45+ 条），但无查询页面，只能到腾讯文档看。
- **建议**：管理员侧增加日志查询（按人/时间/操作类型筛选）。

#### D5 【P2】误操作无法冲销
- **行业惯例**：错误单据用红字冲销单更正，保留痕迹。
- **当前现状**：无冲销/撤销（审批通过、入库登记均不可逆）。
- **建议**：增加"冲销"入口（写反向流水并关联原单），仅限管理员。

#### D6 【P3】权限粒度较粗
- **当前现状**：教师与管理员均可审批/出入库/建档，仅"用户管理"限管理员。
- **建议**：按需细化（如"建档仅管理员""冲销仅管理员"）。

## 5. 建议实施顺序

1. **先修 P0（账务）**：补审批流水 → 补历史 → 建对账工具。这三步做完，"库存对不对得上"才有答案，后续所有统计与报表才可信。
2. **再补 P1 闭环**：扫码即办、学生归还、借期逾期、用途/驳回原因/撤销、导出、盘点、期初。这一步让系统从"能记账"升级为"能管业务"。
3. **然后 P2 效率**：批量、分页、筛选、搜索统一、预警触达。数据量上来后必不可少。
4. **最后 P3 增强**：库位/批次/图片/制码等按实际需要选做。

> 每一步都应保持现有工程质量标准：写操作必须走 `withWriteLock` + `withWriteIdem` + 写后回读校验，改后端后重传云函数并跑一遍回归（`node --check` 全量 + 角色门禁 + 真实数据只读核对）。
