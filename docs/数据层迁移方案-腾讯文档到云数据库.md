# 数据层迁移技术方案：腾讯文档 → 微信云数据库（CloudBase DB）

> 适用：实训室管理系统 `lab-miniprogram`
> 背景：个人开发者无法拿到腾讯文档 OAuth `refresh_token`（无「应用管理」入口），`access_token` 每 30 天必断（当前 token 2026-11-21 到期）。切换到同环境的云数据库，可**永久消除 token 过期问题**，且不增加任何月度费用（基础版免费额度：数据库 2GB / 读 5 万次·天 / 写 3 万次·天 / 并发 20，对本系统绰绰有余）。
> 状态：**✅ C 方案已实施（代码就绪，待云端建集合 + 切 DATA_BACKEND=cloud 验证）**

---

## 0. 决策结论速览

| 项 | 结论 |
|---|---|
| 选 C 的理由 | 个人号无 OAuth 应用入口，A（每 30 天手动）治标、B 走不通；C 一次性改造换取永久 0 运维 |
| 是否增加费用 | **否**。云函数本就跑在 CloudBase 上，仅换数据源；免费额度完全覆盖班级级用量 |
| 改动范围 | 新增 `clouddb.js`（适配器）+ `backend-switch.js`（冗余开关，上一轮已落地）+ `migrate.js`（迁移逻辑）+ `index.js` 新增 `migrate` action；**前端与 `mock.js` 回退零改动** |

## 1. 现状盘点（基于真实代码，非臆测）

### 1.1 三层数据架构
```
小程序前端 pages/**
   │  (wx.cloud.callFunction: docsProxy)
   ▼
cloudfunctions/docsProxy/index.js   ← 调度层（50+ 个 action 的 case 分发 + 权限闸 gAdmin/gStaff/gUser）
   │  生产路径：const td = require('./tencentdocs')
   │  mock 路径：mockHandler（内存演示，USE_MOCK=true）
   ▼
cloudfunctions/docsProxy/tencentdocs.js   ← 防腐层（腾讯文档 API 适配，对外暴露 td.* 接口）
   │
   ▼
腾讯文档 8 张智能表（FILE_ID=DDJvsIIuHZKh，表 ID 见 TABLE 常量）

前端离线回退：utils/mock.js  ← 纯浏览器内实现，与 tencentdocs.js 完全无关，独立可跑

**关键洞察**：`index.js` 的所有 50+ 个 case 都通过 `run(() => td.xxx(data))` 调用 `tencentdocs.js` 导出的函数。**只要新适配器 `clouddb.js` 导出**`与 tencentdocs.js 完全相同`的 `module.exports`，`index.js` 只改一行 `require` 即可切换数据源，业务函数与权限闸全部复用。

## 2. 总体迁移策略（最小风险）

**核心原则：保持接口契约不变，只换存储后端。**

1. **新建 `cloudfunctions/docsProxy/clouddb.js`**，导出与 `tencentdocs.js` **完全一致**的 `module.exports` 对象；内部用 `cloud.database()` 实现。
2. **`index.js` 增加 feature flag**：读取环境变量 `DATA_BACKEND`（默认 `tencent`）。实际切换逻辑已由上一轮落地的 `backend-switch.js` 承载——`resolveEnv()` + `buildChain()` 解析 `USE_MOCK` / `DATA_BACKEND` / `FALLBACK`，构建回退链并把每个后端的 `td` 模块随请求传入 `prodHandler(action, data, openid, tdModule)`（并发安全）。`DATA_BACKEND=cloud` 时链首即 `clouddb` 模块；否则 `tencentdocs`。**`tencentdocs.js` 首版不删**，随时回滚。
3. **前端 `pages/**` 与 `utils/mock.js` 完全不动**（前端只认云函数 `docsProxy` 的 action 协议）。
4. **关键技巧——保持 `{recordId, fields}` 返回形状**：`getRecords` 在云库实现中返回 `{ recordId, fields: {英文key: value} }`，与腾讯文档适配器完全一致。如此一来，`normUser` / `normMaterial` 等几十个业务函数**可原样复制**，仅 `COL` 常量改为英文恒等映射即可编译通过。

> 这意味着迁移的"重写量"被压到最低：业务函数整段搬、只换底层 CRUD。

> **【实施决策·与初稿建议不同，已采纳更优解】** 初稿建议角色/状态"直接用英文枚举"。实际落地改为：**云库字段用英文 key，但枚举值仍存中文**（如 `role='超级管理员'`、`status='待审批'`、`dir='入库'`、`borrow.status='借出中'`），与腾讯文档数据**完全同构**。
> 理由：① `clouddb.js` 的业务函数（`normUser`/`normReq`/`normBorrow`/`normStockIO`…）直接复用 `tencentdocs.js` 的 `TR.*` 中英互转，无需任何改动；② 迁移（migrate）只需把中文列名重命名为英文 key、**值原样搬**，零转换、零丢失，且腾讯文档与云库两份数据可逐字段比对；③ 回滚时云库的中文枚举值与腾讯文档对齐，不会出现"两边语义不一致"。`now()` 返 epoch 毫秒（与腾讯文档日期列落库时间戳同语义），便于排序/报表。腾讯文档"自动编号列"在云库无对应机制 → `requisition`/`toolRequisition` 改为本地 `genNo` 生成单号写入 `id` 字段（迁移时旧单号原样保留）。

## 4. 适配器 `clouddb.js` 实现清单

### 4.1 必须真正实现（对应腾讯文档 CRUD）
| 新函数 | 云库实现要点 |
|---|---|
| `getRecords(table, filterFn?)` | `db.collection(table).get()`；若传 `filterFn`，在内存侧过滤（保持返回 `{recordId, fields}`）。首版可全量取后在 Node 内存过滤（数据量小）；量大时可加 `where` 条件优化。 |
| `addRecord(table, fields)` | `db.collection(table).add({ data: fields })`，返回新 `_id` |
| `updateRecord(table, rid, fields)` | `db.collection(table).doc(rid).update({ data: fields })` |
| `deleteRecordByIds(table, ids)` | 逐条 `doc(id).remove()`（或 `command` 批量） |
| `getItem(id)` | 复用现有逻辑，仅底层走 `getRecords` |
| 业务函数 `requisition / approve / io / borrow / returnTool / stocktake / reverseIO / batchIo / usage / snapshot / adminUpsertUser / ...` | **整段从 tencentdocs.js 复制**，仅 `COL` 改英文映射。写路径的 `withWriteLock`/`withWriteIdem` 可保留（与存储无关）。 |

### 4.2 腾讯文档专属 → 在云库模式下降级为 no-op / 改写
| 原函数 | 处理 |
|---|---|
| `getToken` / `authorizeWithCode` / `callSmart` / `callApi` | no-op（返回 `null`/`{code:0}`），云库无需 token |
| `ensureOpenIdColumn` | no-op（openid 是普通字段，始终存在） |
| `warmFieldMaps` / `getFieldMap` / `buildValues` | no-op（云库无列映射概念） |
| `invalidateCache` / `cacheStats` / `clearFieldMapCache` | 轻量实现：保留内存缓存接口（可选），或简化返回空 |
| `runtimeInfo` | 改写：返回云库连接状态而非 token 剩余天数（影响「我的→云端自检」显示） |

### 4.3 可进阶简化的部分（非首版强制）
- 现有 `verifyStock` 回读校验是为腾讯文档**弱一致、无事务**写的补偿逻辑。云库原生支持**事务**（`db.runTransaction`），可在稳定后把"扣库存+建借还"改成单事务，消除盲写风险。首版先保留锁层，降低回归面。

## 6. 数据迁移脚本

一次性迁移现有腾讯文档 8 表 → 云库 8 集合。

**方案 A（推荐，零额外基础设施）—— ✅ 已实施**：在 `docsProxy` 内新增一次性 action `migrate`（super 管理员可调用），逻辑抽取为纯函数 `clouddb.js` 同目录的 `migrate.js`（可注入、可单测）：
1. 用 `tencentdocs` 适配器读 8 张表全量（走 `getRecords`），`fields` 为**中文列名**做 key；
2. 逐行按 `COL` 把中文列名重命名为英文 key（未知列忽略，保持云库 schema 干净）；值原样搬，其中 13 位时间戳字符串转数字；
3. `clouddb.addRecord` 写入对应集合（写入前先按 `recordId` 清空目的集合，**幂等、可重复执行**）；
4. 返回每表迁移条数（`srcTotal / written / skipped / dropUnknown`）。

- **权限**：`migrate` action 在 `prodHandler` 中校验——身份走**源（腾讯文档）**账号体系 `tencentdocs.whoami(openid)`，仅 `role==='super'` 可调用。刻意不依赖当前后端，避免"切到 cloud 后用户表为空、谁都登录不上、迁移被自身权限闸挡住"的鸡生蛋问题。
- **源数据保留不删**，可回滚：只需把 `DATA_BACKEND` 切回 `tencent`，业务/前端零改动。
- **演示模式（USE_MOCK=true）**下 `mockHandler` 对该 action 返回明确提示（不支持迁移），不会误触真实写入。

**方案 B**：本地 `tools/migrate-to-clouddb.js` 用 `wx-server-sdk` 初始化云环境后执行（需本机配置密钥，较繁琐，未采用）。

> 迁移前先导出腾讯文档为 JSON 备份（`exportData` 已支持 logs/access，可扩展全表导出），确保可回滚。

**迁移顺序建议**：`users` → `materials`/`tools` → 业务流水（requisitions/borrow/stock_io/access/logs）最后，避免外键依赖问题（本系统无硬外键，顺序影响小）。

## 8.1 路径 A 上线手册（你侧执行清单，我侧代码已就绪）

> 前提：阶段 1 代码已交付、`regress-all` 16/16 全绿、源适配器 `tencentdocs.js` 与云库适配器 `clouddb.js`、`migrate.js` 均已随云函数上传。

**① 云开发控制台建 8 个集合**

集合名（**一字不差**）：`users` / `materials` / `tools` / `requisitions` / `borrow` / `stock_io` / `access` / `logs`
每个集合权限设为 **"所有用户不可读写（即仅云函数可读写）"**，禁止客户端直连（否则任何人可绕过云函数改库）。

**② 部署云函数（关键时序）**

- 上传整个 `docsProxy` 目录（务必含 `index.js` / `clouddb.js` / `migrate.js` / `tencentdocs.js` / `backend-switch.js`）。
- **部署时 `DATA_BACKEND` 环境变量先保持 `tencent`（或不设）**：迁移期间系统仍以腾讯文档为主后端，保证业务不中断；`migrate` action 的源已**硬编码为 `tencentdocs`**（`require('./tencentdocs.js')`），不受 `DATA_BACKEND` 影响，所以即便设了 cloud 也不会读错源——但为稳妥，迁移阶段仍建议保持 tencent。
- ⚠ **先确认腾讯文档 access_token 未过期**（原配置约 2026/11/21 到期，见《长期记忆·上线前必做》）。`migrate` 要从腾讯文档读全量，token 失效会读源失败。

**③ 以超级管理员身份调 `migrate`（导入数据）**

⚠ **先调大云函数超时时间**：在云函数 `docsProxy` 配置里把「超时时间」调到最大（如 60s）。迁移要读 8 表全量 + 写云库，默认 3s 极易超时失败。

**用小程序内建按钮（推荐，免踩 openid 坑）**：以 **super 账号（邓老师）** 登录小程序 → 「我的」页最下方「数据迁移 · 腾讯文档 → 云数据库」卡片 → 点「执行数据迁移」。该按钮**仅 super 可见**（`identity.isSuper()` 控制），且用 `api.callFull(..., {noFallback:true})` 直达云函数，不会误回退到 mock。

    { "table": "logs",        "srcTotal": 300, "written": 300,"skipped": 0, "dropUnknown": 0 }
  ] } }
```

- 幂等：重复调用会先清空目的集合再写入，**可放心重跑补齐**（部分失败时用它补齐）。
- 失败处理：返回 `code:500` 且提示"已部分写入" → 修正后再次调用即补齐。
- 非 super 调用 → `code:403`；云库未就绪（`dbReady=false`）→ `code:500` 且**不改动任何数据**。

**④ 翻转后端到云库**

云函数环境变量 `DATA_BACKEND=cloud` → **重新部署**（环境变量在模块加载时读取，必须冷启动生效；重新部署最稳）。
> 注意：`DATA_BACKEND` 由 `backend-switch.js` 在模块加载时解析，改完**必须重部署或等冷启动**，仅改控制台变量不重部署可能仍跑旧实例。

**⑤ 验证**

- 小程序「我的 → 云端自检」显示 **"云库已连接 ✅"**（前端对应 `runtimeInfo().dbReady` 文案，去掉原 token 剩余天数）。
- 真机走完整链路：领用申请 → 教师审批 → 出入库登记 → 工具借还 → 库存盘点 → 报表核对。
- 抽查：云库集合行数 = 腾讯文档行数（一致即迁移完整）。

**⑥ 回滚（随时）**

云函数 `DATA_BACKEND` 改回 `tencent` + 重新部署 → 立即恢复腾讯文档后端（云库数据保留不删）。

## 9. 风险与未确认点（如实标注）

1. **云库免费额度**：基础版实测为 2GB / 读 5 万·天 / 写 3 万·天（2026 新开环境可能改为 40000 资源点/月限 6 个月，之后 ¥19.9/月）。**以你云开发控制台实际显示为准**；即便 ¥19.9/月也远低于自建服务器，对本系统仍"基本免费"。
2. **集合权限规则**：必须设置"禁止客户端直连"，否则任何人可绕过云函数改库。需实现时核实 CloudBase 控制台当前权限选项文案。
3. **`getRecords` 全量取后内存过滤**：数据量极小（百~千行）时无性能问题；若未来全校级（万行+），需改为 `where` 条件下推。首版不优化。
4. **openid 绑定连续性**：云库 `users.openid` 由 `bindLogin` 写入，与现逻辑一致；迁移时原腾讯文档已绑定的 openid 会随数据一起搬过来，用户无需重新登录。
5. **`runtimeInfo` 改写影响「云端自检」UI**：需同步调整前端自检文案（去掉"token 剩余天数"，改为"云库已连接"），否则自检页可能显示异常。
